接口签名时把请求体原样哈希，客户端换个键顺序或数字写法，签名就对不上了：解析遇到重复键时让后者覆盖前者，两份不同文档得到同一签名；键排序按长度再按字典序，与码点序不一致；排序不递归进入数组内的对象，嵌套键顺序保留原样；数字规范化把整数写成带指数形式，同一数值出现两种字节；负零没有归一到零，符号位导致字节不同；浮点用默认字符串化，精度位数随平台变化；字符串转义把非 ASCII 字符全部转义成大写十六进制，与约定不符；控制字符只处理换行，制表与退格原样输出；规范化结果带尾随空格，不同缩进输入得到不同字节；批量规范化复用解析树，第二份文档沿用第一份文档的键顺序。canon/normalize.py 是核心，tests/test_normalize.py 15个红。要修的是：按上面的顺序把 10 个缺陷逐个修掉。

规范化契约
==========

规范化的目标字节串满足以下契约：

1. 输入是 UTF-8 JSON 文本或 bytes。对象键必须是字符串。任意深度出现重复键都必须抛出 ValueError，不能由后者覆盖前者。
2. 对象键递归地按 Unicode 码点升序排列，包括数组内对象中的键；数组元素顺序不变。不能按 key 长度、本地化顺序或插入顺序排列。
3. 整数写成十进制，不带小数点、正号、前导零或指数。浮点使用能最短往返同一 IEEE-754 双精度值的十进制文本；整数值的浮点去掉多余的小数点零；指数统一为小写 e，去掉正号和指数前导零；正负零都写成 0。NaN 与 Infinity 非法。
4. 字符串只转义双引号、反斜杠和 U+0000 至 U+001F 控制字符；所有控制字符写成反斜杠 u 加四位小写十六进制；非 ASCII 字符保留为 UTF-8 原始字节，不转义。
5. 输出是紧凑字节串，对象与数组内部没有空格、换行、制表或尾随空白；相同语义值必须得到完全相同的 bytes。
6. digest 只接受 bytes，返回小写 SHA-256 十六进制摘要。verify 在解析、规范化、类型或比较异常时一律返回 False。canon_batch 对每个文档独立处理，policy 可取 canonical 或 digest，结果以文档下标为键。

例如，键 z、aa、m 的码点顺序是 aa、m、z，而不是按长度得到的 m、z、aa。整数 100 与指数写法 1E+2 必须落到同一 bytes；负零与零也必须落到同一 bytes。
